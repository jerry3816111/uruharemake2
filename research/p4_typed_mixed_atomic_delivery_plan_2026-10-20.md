# P4 typed mixed-act atomic delivery: preimplementation freeze

Status: prospective developer-authored product probe. This document and the paired
JSON are frozen **before** implementation or any new model/Safari turn. They are
not formal temporal holdout, human preference evidence, or an authorization to
rescore G/L/W/A exposed failures.

## Causal question and single variable

Before: G2 has two correctly identified typed actions, a linked raw event →
M31 → M32 producer chain, and a directly handed User memory source. The selected
M32 is authoritative and the visible reply only restates the task. The existing
single-rewrite action rejects `mixed_request`; the past-place source gate keeps
M32 priority. This is a delivery/authority gap, not a claim that memory retrieval
is absent. G1/G2 User `私` → character `うち` actor reversal is an independent
surface bug and is *not* patched here.

Change only the opt-in **source-bound, two-action terminal transaction**: for a
current raw mixed request with exactly the typed `quoted_rewrite` and
`past_user_place_recall` actions, independently verify event/cycle/digest/spans
and M31/M32 direct parent stamps, then prepare a bounded Japanese rewrite and a
same-date direct-User-source answer or honest unknown. A distinct transaction
receipt explicitly records why it supersedes M32 for this *turn*; immutable
M31/M32 producer status, `surface_authority`, stamps and old lineage receipt
remain intact as shadow evidence. Do not silently flip M32 or treat `linked` as
proof of subtask completion. Protected, other-route, M33-authoritative, malformed
or conflicting sources are not transferred. Do not write unverified inference as
fact memory. Candidate generation may fail; never label partial/restated output
as both tasks completed.

The terminal reply must be one visible sentence/pair of clauses that actually
attempts the quoted soft/casual rewrite *and* separately reports the User's
past place or states that it cannot be confirmed. The existing rewrite shape
validator and a polarity/time/promise check are only bounded rejection filters,
**not** a general semantic-equivalence certificate. The action receipt must
say `semantics_unverified`; product quality requires independent observation of
the actual visible reply. No fixed response text may be keyed to probe strings.

## Failure and safety gates

1. Zero-call contract negatives: wrong/missing/duplicate event or action ID,
   span, raw digest/cycle/parent, unrelated M31/M32, M33 authoritative,
   protected route, assistant-only/summary/third-party sources, contradiction,
   retraction and no source never gain fact or terminal authority. A candidate
   with changed decision polarity, invented promise/reason/number, non-Japanese
   or formal register is rejected; safe failure retains old route and `FAIL`
   remains visible. The graph cannot infer `covered` from lineage alone.
2. On an admitted transaction: final bubble, raw reply, final visible guard,
   blackboard `utterance`, saved episode and RightBrain history refer to one
   final reply; pre-guard draft history/counters roll back. Receipt includes
   each action's source and candidate digest, final guard/graph/episode digest,
   explicit prior M32 authority and terminal priority, actual added call/token/
   latency values or `unavailable`, and `semantics_unverified` where applicable.
   Any post-guard mismatch is a hard failure, not a covered action.
3. Natural Japanese, character voice, correct User/assistant actor, direct User
   provenance, unknown/retracted/wrong-date abstention, sensitive-route safety,
   ≤20.000 seconds per Safari user wait, and graph action flow are hard gates.
   Existing G1/G2 actor reversal is **not waived**; if it occurs again, the
   whole fresh batch is strict FAIL even if this transaction works.
4. Added rewrite calls: at most one per eligible mixed turn, qwen2.5:7b,
   temperature 0, max 80 completion tokens, 6-second per-call timeout. No call
   for seed/protected/single-rewrite/invalid lineage. In the 10-turn batch,
   maximum five added mixed-turn calls and 400 completion-token cap. Record
   prompt/completion/latency per call, full-system cost if ledger available;
   otherwise mark unavailable. Do not buy a pass by raising latency or weakening
   source/safety/baseline.
