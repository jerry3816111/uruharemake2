# M45 實作基準：方法必須真的交付

2026-08-29。依已確認的 M45 計畫續作；不修改被 M44 封存的原計畫。

## 單一變因與邊界

只改最後 practical-help 的交付契約，不重選人格、使用者需求或上游策略。
M37–M44 舊核心、測試、題庫、結果保持原樣。使用獨立 opt-in overlay。
研究仍是可修正的人類語用模型；Uruha 是公開人格實例，不是本人或心理真值。

原失敗：選了 solve_regulation，M39 卻把「一起決定一個方法」算成已給方法。
新契約須分開 selected / delivered / awaiting_context / unavailable。

1. 來源只取當輪使用者文字；只有既有 linked correction 時，才可取緊鄰上一輪
   使用者原文。不可用助理回答、摘要、未知遠期記憶填補事實。
2. 本機模型提出有來源錨點的 action / object / observable completion，或明示
   needs_context。這些是建議，不是已發生事實。禁止範例題、答案或任務白名單。
3. 先檢查 source ID、exact span、日文與動作／對象欄位；再由另一個獨立呼叫
   只看原始來源和候選，審核具體交付、相關性、未提供條件、低風險與語氣。
   同模型審核只是 proxy，不宣稱獨立人評或完整語意證明。
4. 最多兩次本機模型呼叫，總額外時間預算 12 秒，不重試。失敗／資訊不足時
   自然短問，標記未交付；不以固定報告答案代替生成。
5. M39 最後 audit 必須反映 M45 未交付，M44 不得替未完成方法補成功紀錄。
   既有當輪 pending 加 typed delivery 註記；未交付的 solve 不得在下一輪被
   確認成方法成功或增加 implicit 校準樣本。原有歷史 outcome 不重寫。
6. runtime graph 展示來源→具体動作→完成條件→交付／待補資訊，並同步同輪
   owner／snapshot／history。使用者回覆不顯示技術分析。

## 驗收

- 開發契約：空承諾、真正動作、錯來源／對象、缺資訊、未知条件、protected
  路徑、非 solve、模型逾時、日文／角色、當輪紀錄／下一輪 outcome、重啟保存。
- 獨立保存 24 個作者自編 typed contract 案例，實作前封存、實作封存後只跑一次。
  舊 M39 關鍵詞檢查為機制對照，不當作 LLM 能力或人類偏好比較。
- 相稱選定回歸，完整報告選取範圍，不宣稱全歷史 suite。
- 新隔離 Safari session：報告停滯後改要方法、不同日常任務、缺必要資訊、
  下一輪支持／糾正／換題及角色身分。每輪核對輸入、回覆、M45 node 及內容；
  正式 DB 前後 hash 相同。已知 M44 問題回歸不稱 unseen holdout。
- 成功判準：可用來源且低風險時有具體步驟；缺資訊時不捏造、不冒算完成；
  trace 和最後可見文字一致；保護路徑及非 solve 不改。若 Web 不成立照實 FAIL。

## 資源和限制

只用已安裝本機模型，不外部部署。兩次生成／審核可能增加整輪延遲，必須分開
報告新增呼叫成本與 Web 等待。不能藉此宣稱讀懂所有隱含需求、廣泛人物預測、
盲評優勢或完整人腦方程式。原入口繼續凍結，不將所有未提交修改混入 commit。
